### Bugs found and fixed along the way (worth remembering)
- **`_omml_text` does not XML-escape.** A literal `<` in "P < AVC" silently
  produced an invalid slide part. `_build_Module4.py` wraps both OMML text
  helpers with an escaping version rather than fixing every call site.
- **`make_diagram_slide` already draws the footer.** Seventeen slide
  functions called `_draw_footer` again, doubling the footer.
- **The animation engine's chrome heuristic** treated any large textless
  `sp` as a white chart backing, which is exactly what a custGeom curve
  looks like — every curve was being left static. It now also requires a
  preset rect with a solid fill.
- **`t:` selectors could resolve to chrome.** `t:S#1` on the sales-tax
  slide matched the TITLE ("Sales Tax: …") instead of the supply label, so
  the title faded in on click 1. Text selectors now search content shapes
  only, which also makes the `#n` indices match the inventory listing.
- **The helper generator took the FIRST definition of a redefined name**,
  so `_draw_footer` came out as the static-text version instead of Module
  1's live `slidenum` field override. Last definition now wins.
- Bash heredocs on this machine eat one backslash level — every patch
  script had to be written with the Write tool and run by path.

### Hand-edit port - how it was verified
`_diff_slides.py` decodes every shape in two decks to its RENDERED
position in inches (group children included, through the chOff/chExt
transform), matches by type + normalised text, and compares to 0.01".
Run against a full side-path rebuild it reported exactly one real
difference - slide 81's picture. The other 15 flagged slides were the
documented artefact: a PowerPoint save wraps every OMML textbox in
`mc:AlternateContent`, after which python-pptx stops enumerating it, so
the equation slides read as phantom deletions.

### The bug worth remembering
**`_fig_curve` was building `<a:ln>` with `ET.SubElement`**, which appends
- so the element landed AFTER the `<a:effectLst>` that
`shadow.inherit = False` had just added. Inside `<a:spPr>` the order is
xfrm -> geometry -> fill -> ln -> effectLst, and an out-of-order `<a:ln>`
is silently ignored: every custGeom curve in the deck was falling back to
the shape's theme line, a thin light-blue 1 pt stroke, instead of the navy
/ gold weight the chart asked for. The fix is to go through
`shape.line`, which uses `get_or_add_ln()` and inserts at the right point.
Same family as the documented "`<a:solidFill>` must come BEFORE
`<a:latin>` inside `<a:rPr>`" trap - and it is invisible unless you
actually look at a render.

Two smaller ones: the animation plans name chart labels by their text, so
switching the numbers renamed six of them (the engine raises KeyError on
an unresolved selector, which is the failure mode we want); and the
profit rectangle on slide 25 was painted over the ATC curve, so the region
is now drawn before the curves.

40-acre plot, UF/IFAS NE Florida cabbage budget (Aug 2025) for the input

So the deck's cost function is no longer "the MW numbers" - it is the
output of a sourced model, and `_cabbage_numbers_check.md` now says so.

what makes the worked example come out at TR = $265,000. Left at $400 and
flagged; aligning them is one cell either way (deck `P_HIGH` = 425.70, or
spreadsheet B77 = 444.44 which nets exactly $400).
